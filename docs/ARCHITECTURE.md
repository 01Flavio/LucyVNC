# Architecture and security boundaries

## Implemented in this build

- `LucyVNC.Manager.exe` is the WPF Manager / Viewer. `MainWindow` manages saved computers and outgoing sessions; `RemoteWorkspaceWindow` is a separate taskbar/Alt+Tab window containing Viewer tabs.
- Each open tab retains its own `VncViewerSession`, framebuffer bitmap, input state and continuous receive loop. Selecting another tab changes only which framebuffer is displayed; it does not stop or recreate the other session. Closing a tab disposes only its session. The Manager keeps disconnected sessions visible for explicit reconnection.
- Framebuffer deltas are accumulated per session and rendered through at most one queued WPF Dispatcher operation at `Background` priority. A pending dirty rectangle is merged with newer patches, so recursive/self-mirror or fast updates replace stale presentation work instead of building an unbounded UI queue; input and dialog interaction retain dispatcher priority. No network I/O runs on the UI thread.
- Development diagnostics use `Trace` in Debug builds for authenticated connection, Workspace creation, save-computer dialog open/close, first rendered frame, render failures, disconnect requests, and session cleanup. They omit passwords and framebuffer contents. Disconnect cancels the receive loop, bounds remote input release to two seconds, and waits up to five seconds for loop termination before reporting the condition.
- The Remote Workspace closes after the last tab is removed and the Manager clears its window reference on `Closed`. A new connection creates a fresh Workspace. Closing the Workspace with tabs open asks once for confirmation; accepted session cleanup is deferred until the cancelled WPF `Closing` event has returned. An empty Workspace action in the Manager returns to computer selection instead of opening a blank window.
- `Vnc.Infrastructure.LocalComputerStore` creates `%LOCALAPPDATA%\LucyVNC\lucy.db` and applies schema migrations through version 2. The schema stores computers, favorites, groups, display preferences, sort preference, connection history, and only a validated Credential Manager target reference. Password values are rejected by the store.
- The Manager asks for a VNC password when no endpoint credential is available. Remembering it is an explicit opt-in and uses the signed-in user's Windows Credential Manager; the endpoint key includes normalized host and port. A remembered password rejected by the peer is deleted and replaced only after another user prompt. Passwords are never logged or written to SQLite.
- Manager and Workspace use the shared dark-purple WPF resource dictionary. The computer list is presented as selectable cards; its connect actions use the same session de-duplication and lifecycle path as double-click.
- `Vnc.Protocol` remains the shared RFB implementation. `Vnc.Viewer` owns each outbound TCP connection; individual session state and input are isolated.
- `Vnc.Server` is the RFB server library and is consumed by the Server Worker, not by the Manager project. `Vnc.Platform.Windows` provides GDI and `SendInput` to the Server Agent.
- `Vnc.Service` is a .NET 8 Worker Service host registered under SCM name `LucyVNCService`. It validates its configuration and waits for an authenticated interactive-session Agent before opening the existing RFB server. The listener requires VNC Authentication, is limited to loopback/private/VPN/link-local bind addresses, allows one client, and closes when Agent heartbeats fail. After a recoverable Agent/IPC failure the Worker retries; console mode is provided for controlled development tests.
- `Vnc.Agent` captures the logged-in interactive desktop and applies remote input through the existing Windows platform adapters. It checks `OpenInputDesktop` and the desktop name before accepting IPC/capture/input; only an available `Default` desktop is supported. Its named pipe ACL permits the hosting user and configured Worker SID; the Agent obtains the real client SID by pipe impersonation rather than trusting a JSON claim. The Worker queries the pipe-server process identity and negotiates the IPC version. Message sizes, frame dimensions, heartbeat waits, and input release are bounded. This proves user-SID identity, not binary identity: another process running as the same user is not separated by this mechanism.
- The Manager has no direct project reference to `Vnc.Service`, `Vnc.Agent`, `Vnc.Server`, or `Vnc.Platform.Windows` and no server/service settings or control handlers. Its published dependency manifest must not contain Server Worker, Agent, or RFB Server libraries.
- `LucyVNC.Server.exe` is the independent WinForms notification-area and Server Configuration application. Its configuration window writes settings through the elevated `LucyVNC.Server.Worker.exe --configure` helper. Defaults are sharing disabled, loopback, port 5901, mandatory authentication, and one session. Production settings live under `%ProgramData%\LucyVNC\Service\service.json`, ACL-restricted to SYSTEM/Administrators with read-only access for the configured Agent SID. The VNC password is stored separately as DPAPI LocalMachine ciphertext with SYSTEM/Administrators ACLs.
- The Server application installs, starts, stops, restarts, and removes the Windows Service only through explicit user action and UAC. Setup installs/updates the service only when the Server component is selected and the user checks the install-consent option. Startup can be Automatic or Manual; setup does not create firewall rules. A per-user Run registration starts `LucyVNC.Server.exe` after the authorized interactive user's logon; the Server app supervises one Agent with bounded exponential backoff.
- The Server tray/configuration app does not open or depend on the Manager. It reports SCM and runtime status, provides service actions, and lets the user open Server Configuration. Exiting the tray does not stop the Worker or Agent. A non-secret runtime JSON status file distinguishes SCM state from authenticated Agent/listener readiness.
- The Worker and Agent are separate processes. The Agent supervisor and Agent use per-user-session mutexes. Logoff ends interactive processes; the next authorized logon can restart them through the per-user registration. On boot before logon, the Worker keeps the RFB listener closed until an authorized Agent authenticates and the interactive desktop is available.
- The Inno Setup package includes independent Manager and Server components, selected separately or together. Manager files are installed in the application root; Server Worker, Agent, tray/configuration app, and scripts are placed under `Server`.
- SCM installation, Worker-as-SYSTEM to interactive-user Agent authorization in a real installed service, Windows logon startup, reboot recovery, lock/unlock, user switching, and session lifecycle integration have not been validated. Running Worker and Agent under the same interactive Windows account in development tests does not establish that production security boundary.
- `Vnc.Infrastructure.SavedComputerImportExportService` reads/writes version-1 JSON (`schemaVersion`, `computers`) and header-based CSV. It validates each record, normalizes endpoint aliases for duplicate/conflict detection, previews an import plan, and applies creates/updates in one SQLite transaction. Conflicts default to Ignore. Updates replace portable settings but retain local favorite/history/credential fields; import records cannot provide Credential Manager references. Export supports all records, favorites, and selected IDs, and excludes IDs, history, and all secrets. The Manager limits selected import files to 10 MiB.
- The Manager session list is not a framebuffer host. `RemoteWorkspaceWindow` owns presentation tabs and is separate from the Manager; an individual session tab cannot yet be detached into a second workspace window.
- Classic VNC authentication remains unencrypted and has the protocol's effective eight-character ASCII password limit. Windows Credential Manager protects stored credentials at rest for the current Windows user; it does not encrypt the RFB network traffic.

## Not yet implemented

- Service-controlled launch/attach of the Agent in the logged-in user's session. A per-user startup registration launches the independent Server tray and Agent supervisor instead; this still requires the user to log on and does not broker session changes.
- Real Windows desktop capture and actual `SendInput` validation for the Worker/Agent service path. The current cross-process test uses synthetic capture/input endpoints; it does not start the production Agent executable or inject input into a real desktop.
- Authentication-attempt limiting, richer connected-client diagnostics, and audit records.
- Session 0 capture/input, secure-desktop access, UAC bypass, pre-login control, and automatic recovery across user/session switches. The service deliberately does not attempt control when the interactive `Default` desktop is unavailable.
- Real Windows service installation/start/stop, UAC-mediated Server Configuration flows, per-user logon startup, and tray behavior have not been exercised in this environment; the installer must be compiled and separately installed for manual acceptance.
- Detaching a single session tab into a different independent workspace window and re-grouping it elsewhere. The current workspace window itself can be moved between monitors.
- WPF lifecycle tests exercise closing the only tab, retaining a two-tab Workspace until its last tab closes, repeated reopen cycles, close-confirmation cancellation/acceptance, manager shutdown, empty-window actions, and maximized-state preservation. These tests use synthetic tabs; live VNC connection teardown remains covered by the separate network integration tests for simultaneous sessions, framebuffer/input isolation, continued delivery to the remaining session after a peer closes, and reconnect to the released endpoint. Credential target normalization, schema migration, database rejection of secret-like values, and an isolated Windows Credential Manager write/read/delete round-trip have automated coverage.

These are deliberate gaps, not working features behind a UI. The Manager contains no Server controls. The Worker can serve a desktop only when a compatible interactive Agent is authenticated and the supported desktop is available. Service installation, service startup, per-user Agent startup, and firewall changes are all separate actions; no firewall rule is created automatically.

## Required design constraints for the service phase

1. Keep the network listener and RFB protocol independent from the Viewer UI.
2. The service must not call GDI capture or `SendInput` from Session 0. A separately launched user-session agent must perform those operations only after an explicit user enable action.
3. Restrict the agent IPC endpoint to the intended service and logged-in user/session. Authenticate the peer identity in addition to using a random pipe name; bound message sizes and reject malformed or stale requests.
4. Keep remote sharing disabled until the user enables it. Do not implement secure-desktop capture, UAC bypass, hidden persistence, or silent administrative changes.
5. Store no passwords in logs. If persistent credentials are later offered, require explicit opt-in and use Windows Credential Manager or DPAPI with an ACL appropriate to the service identity.
6. Preserve loopback/private/VPN interface authorization, required authentication, current session limit policy, and deterministic release of pressed input on every disconnect and service stop.

## Connection import/export schema

Native JSON is an object with `schemaVersion: 1` and a `computers` array. Each object contains only `name`, optional `hostname`, optional `ipAddress`, `port`, optional `group`, `isFavorite`, and `viewPreference` (`fit` or `100%`). At least one of hostname or IP is required. CSV has the columns `name,hostname,ipAddress,port,group,isFavorite,viewPreference`; `name` and `port` are mandatory, and an empty favorite value means false.

Import planning reports invalid records, repeated endpoints within the file, and conflicts with saved endpoints. Endpoint matching is by any normalized hostname/IP alias plus port, so a saved hostname paired with the same imported IP can be a conflict when the saved record contains both aliases. A plan applies atomically to SQLite; conflict policy is Ignore by default, with explicit Update and Create options. Update preserves the target record's favorite flag, last connection history, and stored Credential Manager target. Export includes settings only and is suitable for migrating records, not credentials.

The current foreground Server is suitable only for interactive, explicit testing; it is not a substitute for the planned service and session-agent model.
